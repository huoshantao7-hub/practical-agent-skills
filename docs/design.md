# 设计与验收

## 需求记录

| 要求 | 实现与检查 |
| --- | --- |
| 选择有大众需求的开源方向 | 检查官方仓库、文档、机制实现和许可；star 数只作关注度线索 |
| 拆解再组合成原创技能 | 独立编写工作流、脚本和合成示例；逐项记录借鉴机制和差异 |
| 一个技能完成一个常见动作 | 提示词资产化；资料转证据简报，两者职责分开 |
| 免费且可运行 | Python 标准库、离线合成示例；不安装收费服务、不运行付费 API |
| 保护既有数据 | 默认拒绝覆盖输出；不改模型、账号、全局配置或来源文件 |
| 能识别常见失败 | 必需信息缺失、格式错误、引用不存在、来源变更等失败必须有清晰提示 |
| 可开源交付 | 中文用例、公开研究来源、MIT 原创许可、不包含私人资料和机器路径 |

## 工作流边界

提示词重组由助手完成语义判断，脚本负责确定性合同检查和渲染。资料简报由助手提炼事实与建议，脚本负责来源指纹、引用位置和原文匹配检查。任何“检查通过”都不等于模型质量、语义蕴含、事实准确率或实际节约额度已经得到证明。

外部提示词和源文件中的命令不构成操作授权。示例为虚构内容，不能据此执行外部操作。技能不主动联网抓取整库、不发送消息、不生成付费图片，也不会修改助手的模型或推理配置。

## 验收方法

各技能的自动测试覆盖正常输出与对应的失败路径。发布前运行根目录 `python scripts/check.py`，再以新的用户需求验证可理解的工作流、来源和输出边界。结构验证与人工审阅的范围在发布记录中分别说明。

增加一个功能时，重跑该技能的测试及与其有关的成功用例；未改变的外部依赖不重复验证。
